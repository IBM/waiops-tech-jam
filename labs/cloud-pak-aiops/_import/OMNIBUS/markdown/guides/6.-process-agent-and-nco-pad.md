# 6. Managing OMNIbus Processes with Process Agent and nco_pad

The Process Agent (`nco_pad`) is the Netcool/OMNIbus process-control component. It provides a centralized mechanism for defining, starting, stopping, monitoring, and—when configured—restarting ObjectServers, probes, gateways, and supporting scripts. Administrators can manage an individual process or operate on a logical group of processes called a *service*.

Process Agent reads its configuration from `nco_pa.conf`. That file defines:

- **Processes** — named commands that Process Agent can launch and supervise, including the command line, host, operating-system account, restart behavior, and process type.
- **Services** — logical groups of related processes that can be started or stopped together.
- **Startup behavior** — whether a service starts automatically when `nco_pad` starts or requires manual intervention.
- **Process monitoring and recovery** — whether Process Agent monitors a child process and how it responds when that process exits.
- **Routing** — the Process Agent instance and host information used by process-control clients and PA-aware components.

Process Agent administration is controlled by the authentication mode configured for the daemon. In a normally authenticated environment, an administrator must be a member of the system `ncoadmin` group and uses their Unix account password when running commands such as `nco_pa_status`, `nco_pa_start`, `nco_pa_stop`, and `nco_pa_shutdown`. This lab starts `nco_pad` with `-authenticate NONE` so that authentication is disabled for the training environment; therefore, press Enter at the login or password prompt instead of entering Unix credentials.

A process definition does not start a component by itself. The process must also be assigned to a service. When a service is configured with `ServiceStart = Auto`, Process Agent starts that service when the daemon starts. Administrators can also use process-control commands and tools to start, stop, or check the status of a named process or service.

Netcool/OMNIbus distinguishes between PA-aware and non-PA-aware processes. Components such as the ObjectServer can register with and communicate directly with Process Agent, allowing Process Agent to track their lifecycle and use dependency relationships. Most probes are non-PA-aware processes: Process Agent can launch and monitor them, but the probe does not communicate directly with Process Agent or participate in PA-aware process dependencies. IBM defines a `PaNOT_PA_AWARE` process as one that cannot communicate with the Process Agent and is unaware that it was started by it.[ibm](https://www.ibm.com/docs/en/netcoolomnibus/8.1?topic=components-processes)

In this lab, the ObjectServer is already managed by Process Agent as the `MasterObjectServer` process in the `Core` service. You will extend `nco_pa.conf` to define the `nco_p_syslogd` and `nco_p_mttrapd` probes as managed, non-PA-aware processes. You will then group them in a new `Probes` service and configure that service for automatic startup.

After updating the configuration, you will restart the Process Agent and validate:

- The `Core` service starts and the ObjectServer is running.
- The `Probes` service starts both probe processes.
- `nco_pa_status` reports the expected process and service status.
- Individual probes can be stopped and started without stopping the ObjectServer.
- The complete `Probes` service can be stopped and started as a single operational unit.

This arrangement provides a simple operational model: the ObjectServer remains the core event-management service, while the Syslogd and MTTrapd probes are managed together as event-ingestion processes.

## What Process Agent manages

The Process Agent daemon is `nco_pad`. In this lab, it runs as the `NCO_PA` server and reads its configuration from:

```text
$OMNIHOME/etc/nco_pa.conf
```

The configuration contains three related kinds of entries:

- A **process definition** describes how to start one managed process.
- A **service definition** groups processes for coordinated startup and shutdown.
- A **routing table** identifies the Process Agent server available on the host.

The initial configuration contains one managed process, `MasterObjectServer`, in the `Core` service. The probe definitions added in this lab are managed by Process Agent but are not Process Agent-aware, so they use `PaNOT_PA_AWARE`.

### 6.1 Adding probe process definitions and the Probes service

#### Objective

Add the syslogd and MTTrapd probes as managed Process Agent processes and group them in an automatically started `Probes` service.

#### Background

A Process Agent process definition supplies the command and operating context used to start a process. The `Managed` attribute tells Process Agent to monitor the process. With `RetryCount = 0`, Process Agent does not automatically retry a process after it exits; the lab will explicitly demonstrate stop and start operations later.

The `Probes` service is a non-master service. Its processes are independent of the `Core` master service, so stopping `Probes` does not stop the ObjectServer.

#### Tasks

1. Create a backup of the current Process Agent configuration before editing it:

   ```bash
   cp $OMNIHOME/etc/nco_pa.conf $OMNIHOME/etc/nco_pa.conf.before-lab6
   ```

2. Open the Process Agent configuration:

   ```bash
   vi $OMNIHOME/etc/nco_pa.conf
   ```

3. Add the following process definitions after the existing `MasterObjectServer` process definition:

   ```text
   nco_process 'SyslogdProbe'
   {
           Command '$OMNIHOME/probes/nco_p_syslogd -server EVENTS -rulesfile $OMNIHOME/probes/linux2x86/syslogd-training.rules' run as 0
           Host            =       'ibm-training-server1.ibmtraining.org'
           Managed         =       True
           RestartMsg      =       '${NAME} running as ${EUID} has been restored on ${HOST}.'
           AlertMsg        =       '${NAME} running as ${EUID} has died on ${HOST}.'
           RetryCount      =       0
           ProcessType     =       PaNOT_PA_AWARE
   }

   nco_process 'MttrapdProbe'
   {
           Command '$OMNIHOME/probes/nco_p_mttrapd -server EVENTS -rulesfile $NC_RULES_HOME/snmptrap.rules' run as 0
           Host            =       'ibm-training-server1.ibmtraining.org'
           Managed         =       True
           RestartMsg      =       '${NAME} running as ${EUID} has been restored on ${HOST}.'
           AlertMsg        =       '${NAME} running as ${EUID} has died on ${HOST}.'
           RetryCount      =       0
           ProcessType     =       PaNOT_PA_AWARE
   }
   ```

   **Use the actual fully qualified hostname of the lab server instead of the example shown here.** In this example, the fully qualified hostname is `ibm-training-server1.ibmtraining.org`; replace it with the server name assigned to your lab environment.

4. Add the following service definition after the existing `Core` service definition:

   ```text
   nco_service 'Probes'
   {
           ServiceType     =       Non-Master
           ServiceStart    =       Auto
           process 'SyslogdProbe' NONE
           process 'MttrapdProbe' NONE
   }
   ```

5. Save and close the file.

6. Review the edited configuration and confirm that:

   - `SyslogdProbe` uses the training syslogd rules file.
   - `MttrapdProbe` uses `$NC_RULES_HOME/snmptrap.rules`.
   - Both processes use the correct host and `PaNOT_PA_AWARE`.
   - The `Probes` service is `Non-Master` and `Auto`.
   - Both probe processes are listed in the `Probes` service.

#### Validation

The exercise is successful when:

- A backup of the original configuration exists.
- Both process definitions are present in `$OMNIHOME/etc/nco_pa.conf`.
- The `Probes` service contains both probe processes.
- The original `Core` service and `MasterObjectServer` definition remain unchanged.

#### Expected result

The Process Agent configuration contains the ObjectServer, two managed probes, the existing `Core` service, and the new automatically started `Probes` service.

## Process Agent routing table

The `nco_routing` section identifies the Process Agent instances that can be contacted for process-control operations. It maps a host name to the name of the Process Agent running on that host.

```text
nco_routing
{
   host 'ibm-training-server1.ibmtraining.org' 'NCO_PA'
}
```

In this example:

- `ibm-training-server1.ibmtraining.org` is the host on which the Process Agent is running.
- `NCO_PA` is the Process Agent's configured server name.
- The entry tells Netcool/OMNIbus process-control clients where to send requests for that Process Agent.

For example, when an administrator uses a process-control command or GUI to request the status of `SyslogdProbe`, start the `Probes` service, or stop `MasterObjectServer`, the client uses this routing entry to locate the `NCO_PA` Process Agent on `ibm-training-server1.ibmtraining.org`.

## Local and remote control

Even on a single-host lab system, the routing table is useful because it gives the Process Agent a named, consistent control endpoint. In a distributed deployment, the same concept allows centralized process control across multiple hosts.

For example:

```text
nco_routing
{
   host 'omnibus-core-01.example.net' 'NCO_PA_CORE'
   host 'probe-host-01.example.net'   'NCO_PA_PROBES_01'
   host 'probe-host-02.example.net'   'NCO_PA_PROBES_02'
   host 'gateway-host-01.example.net' 'NCO_PA_GATEWAYS'
}
```

A process-control client can then connect to the appropriate Process Agent and manage processes on that host without requiring a separate login to every server.

## Secure-mode entries

The optional `user` and `password` values are used only when the **target** Process Agent runs in secure mode. The named account must belong to the UNIX `ncoadmin` group on the target host.

Conceptually, a secure-mode route can look like this:

```text
nco_routing
{
   host 'probe-host-01.example.net' 'NCO_PA_PROBES_01' 'netcooladmin' 'encrypted-password'
}
```

Do not store clear-text passwords in `nco_pa.conf`. Use `nco_pa_crypt` to generate the encrypted form required by the configuration.

## What it does not control

The routing table does not define process commands, services, startup order, or restart behavior. Those are defined elsewhere in `nco_pa.conf`:

- `nco_process` defines what command Process Agent starts.
- `nco_service` groups processes for operational control.
- `nco_routing` identifies where a Process Agent can be reached for control requests.

For this lab, the routing section simply declares that the local Process Agent named `NCO_PA` is running on `ibm-training-server1.ibmtraining.org`.
