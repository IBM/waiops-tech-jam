## 8. Making a Java call

IPL gives you direct access to the Java runtime through the `JavaCall` function. This means any Java class available on the Impact server's classpath — whether from the standard library or a custom JAR — can be invoked from policy code. The result can be used immediately in IPL, giving you access to the full breadth of Java functionality without leaving the policy editor.

This section demonstrates the pattern using `java.util.Arrays.sort()`, a straightforward example that is easy to verify and clearly illustrates the calling convention. The same pattern applies to any static method or instance method on any Java class.

### 8.1 Write a policy that sorts an array using a Java call

#### Objective

In this exercise, you will write a policy that builds an IPL array of strings, calls the static Java method `java.util.Arrays.sort()` to sort it in place, and logs the result. By the end of the exercise, you will understand the four-argument `JavaCall` signature and how IPL arrays map to Java arrays.

#### Prerequisites

- Completion of sections 4 through 6, or familiarity with IPL policy creation.
- You are logged in to the Impact GUI.

#### Background

##### The JavaCall function

`JavaCall` has the following signature:

```ipl
JavaCall(ClassName, ObjectInstance, MethodName, { arg1, arg2, ... });
```

| Argument | Purpose |
|---|---|
| `ClassName` | Fully qualified Java class name (e.g. `"java.util.Arrays"`) |
| `ObjectInstance` | The Java object to invoke the method on. Use `null` for static methods |
| `MethodName` | The method name as a string (e.g. `"sort"`) |
| `{ arg1, ... }` | An IPL array of arguments to pass to the method |

For static methods — methods that belong to the class rather than a particular instance — pass `null` as `ObjectInstance`. `java.util.Arrays.sort()` is a static method, so the call looks like:

```ipl
JavaCall("java.util.Arrays", null, "sort", { words });
```

IPL arrays passed to `JavaCall` are automatically bridged to Java arrays and back. When `sort` is called, it sorts the array *in place*, meaning the original `words` variable in IPL reflects the sorted order immediately after the call returns — no return value needs to be captured.

#### Tasks

1. Select the **Policies** tab from the top navigation bar. In the toolbar, click the **dropdown arrow** next to the New Policy icon and select **IPL Policy**.

2. Click the **Save** icon, enter `AA_JavaSortDemo` in the **Policy Name** field, and click **Save**.

3. Enter the following policy code in the editor:

   ```ipl
   /*
    * Policy: AA_JavaSortDemo
    * Purpose: Demonstrate JavaCall by sorting an array of strings using
    *          the static method java.util.Arrays.sort().
    * Trigger: PolicyActivator (run manually via a one-time activation).
    */

   /* Build an unsorted array of strings. */

   words = {"zipper", "apple", "carrot"};

   Log("AA_JavaSortDemo: before sort: " + words);

   /* Call the static Java method java.util.Arrays.sort().
    * null = no object instance (static call).
    * The array is sorted in place — words is updated directly. */

   JavaCall("java.util.Arrays", null, "sort", { words });

   Log("AA_JavaSortDemo: after sort: " + words);
   ```

4. Click the **Syntax Check** icon. Confirm the **Syntax check successful** dialog appears, then click **Close**.

5. Click the **Save** icon to save the policy.

6. Open a terminal on the Impact server. The policy log file is not created until the policy runs for the first time, so create it now so that `tail` has a file to follow:

   ```bash
   touch $IMPACT_HOME/logs/NCI_policylogger_AA_JavaSortDemo.log
   ```

   Then start a live tail:

   ```bash
   tail -f $IMPACT_HOME/logs/NCI_policylogger_AA_JavaSortDemo.log
   ```

   Leave this terminal open — output will appear here as soon as the policy runs.

7. Back in the Impact GUI, with `AA_JavaSortDemo` open in the policy editor, click the green **Run** icon in the toolbar to execute the policy immediately.

   > **Note — the Run icon is a useful testing tool.** Any policy can be run on demand this way, without attaching it to a service. The Run dialog also lets you supply parameter values before execution, which is convenient for testing policies that read named parameters. If you are developing a policy that will eventually be driven by an OMNIbusEventReader, you can stub out the event at the top of the policy code — create an `EventContainer` object explicitly and populate its fields — then use Run to test the logic before the event reader is wired up.

   Confirm the **Policy executed successfully** dialog appears, then click **Close**.

8. Switch back to the terminal. You should see two log entries appear:

   ```
   AA_JavaSortDemo: before sort: [zipper, apple, carrot]
   AA_JavaSortDemo: after sort: [apple, carrot, zipper]
   ```

   Confirm that the array is in alphabetical order after the `JavaCall`.

#### Validation

The exercise is successful when all of the following are true:

- The `AA_JavaSortDemo` policy is saved and the syntax check passes.
- The policy log shows both the before and after arrays, with the after array in alphabetical order.
- You can describe the four arguments of `JavaCall` and explain when to pass `null` as the second argument.
- You can explain the difference between a static method call and an instance method call in this context.

#### Expected result

You have demonstrated that IPL can bridge directly into the Java runtime. The `JavaCall` pattern — class name, instance (or null), method name, argument array — works for any accessible Java method. In production, this is used to invoke custom utility classes (string parsers, encryption helpers, web service clients) from within Impact policy code without requiring a separate integration layer.
